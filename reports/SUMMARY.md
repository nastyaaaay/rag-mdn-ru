# Итоги проекта

Система отвечает на вопросы по русской документации MDN, опираясь только
на её текст, и **измеряет, насколько сама себе врёт**. Этот файл — сводка
результатов; как они получались, с ошибками и тупиками, описано
в [PLAN.md](../PLAN.md).

## Что построено

| Слой | Решение |
|---|---|
| Корпус | 1429 документов MDN на русском → **1323** после фильтра качества |
| Фрагменты | **7895**, медиана 515 символов |
| Эмбеддинги | `multilingual-e5-large`, локально, 1024 измерения |
| Хранилище | PostgreSQL 17 + pgvector, индексы HNSW и полнотекстовый |
| Генерация | OpenAI-совместимый протокол, по умолчанию локальная Ollama |
| Интерфейс | HTTP-API + веб-страница, весь стек в Docker Compose |
| Тесты | **190**, из них 20 работают с настоящей базой |

## Измеренное качество

### Поиск (52 вопроса, метрики без языковой модели)

| Способ | Recall@1 | Recall@5 | MRR |
|---|---:|---:|---:|
| векторный | **43%** | 64% | **0.528** |
| векторный без фрагментов кода | 40% | **67%** | 0.521 |
| гибридный | 38% | 64% | 0.497 |
| полнотекстовый | 5% | 7% | 0.056 |

Recall@5 по типам вопросов (векторный поиск):

| Тип вопроса | Recall@5 |
|---|---:|
| прямой, терминами документации | **93%** |
| требующий нескольких документов | 80% |
| заданный своими словами | 50% |
| **различение похожих страниц** | **30%** |

### Честность ответов (метрики без языковой модели)

| Метрика | Значение |
|---|---:|
| Корректные отказы на ловушках | **60%** (6/10) |
| Ложные отказы | 7% (3/42) |
| Выдуманные ссылки | **0%** (0/52) |
| Точность цитирования | 67% (18/27) |

### Обоснованность и цена этой цифры

| Что | Значение |
|---|---:|
| Обоснованность **по мнению судьи** | 94% (43 ответа) |
| **Согласие судьи с независимой разметкой** | **63%** (19 ответов) |
| Обоснованность **по разметке** | **68%** |

Цифру 94% использовать нельзя, и это главный результат раздела.

## Шесть выводов, которые нельзя было получить рассуждением

**1. Модель-судья систематически завышает оценку.** Из 19 размеченных
ответов судья разошёлся с разметкой в 7 — и **все семь раз в одну сторону**,
в пользу системы. Ни разу не занизил. Это не шум, а сдвиг.

Хуже того: судья одобрил **все четыре выдумки на ловушках**. Ответы про
`navigator.geolocation.getCurrentPosition()` и `getUserMedia()` — методы,
которых в корпусе нет вообще, — он счёл «подтверждающимися фрагментами».
Туда же выдумка про код 301.

Вывод, ради которого и делалась проверка судьи: **LLM-судья без измерения
его собственной точности бесполезен**. Он показал бы 94% обоснованности
и скрыл ровно те случаи, которые проект был призван находить. Метрики,
посчитанные кодом (доля отказов, выдуманные ссылки), оказались надёжнее
оценки языковой модели.


**2. Гибридный поиск оказался хуже простого векторного.** Он стоял способом
по умолчанию из общего соображения «два способа лучше одного». Измерение
показало обратное: полнотекстовый поиск даёт 7% и в объединённой выдаче
тянет результат вниз, а не помогает.

**3. Средняя цифра скрывает диагноз.** Recall@5 = 64% выглядит приемлемо,
пока не разложить по типам вопросов: 93% на прямых против **30%** на
различении похожих страниц. Система уверенно определяет тему и не различает
конкретные методы внутри неё — тексты у соседних страниц справочника почти
дословно совпадают.

**4. Ссылки честные, содержание — нет.** Модель ни разу не сослалась на
несуществующий фрагмент (0 из 52), но выдумывает: добросовестно ссылается
на реальный фрагмент и приписывает ему чужое содержание. Пример — ответ про
код 301 со ссылкой на фрагмент о 308, при том что во фрагментах написано
про 303. Автоматическая проверка ссылок такую подмену не ловит вовсе.

**5. Ловушки пробиваются предсказуемо.** Темы, которых в корпусе нет совсем,
отклоняются надёжно. Там, где тема **мельком упоминается** (`addEventListener`
встречается в текстах 42 раза), модель достраивает ответ из собственных
знаний вопреки прямому запрету в промпте. Это воспроизводимый механизм
отказа, а не «иногда врёт».

**6. Проверка на двух примерах обманывает.** На шаге 6 модель уверенно
различила `Math.acos` и `Math.asin` — и создала впечатление, что с похожими
страницами всё хорошо. На полном индексе из 7895 фрагментов та же задача
даёт 30%.

## Что осталось несделанным

Честный список, а не умолчание:

* **Сравнение размеров фрагмента не проводилось.** Каждый вариант требует
  полной переиндексации — около двух часов при нынешней скорости
  (2 фрагмента в секунду на процессоре). Нужен расчёт на видеокарте.
* **Разметку для проверки судьи делал ассистент, а не человек.** Это
  ослабляет проверку: две языковые модели могут ошибаться согласованно.
  Файл `eval/judge_labels.json` готов к тому, чтобы его перечитал человек.
* **Модель генерации срывается на китайский** в двух ответах из 43
  (`qwen2.5` — китайская модель). Содержание при этом верное, но для
  пользователя ответ негоден. На сервере есть `gemma3:12b` и `gpt-oss:20b` —
  сравнить их не успели.
* **Различение похожих страниц не улучшалось.** Диагноз поставлен, лечение
  не пробовалось. Напрашивающаяся идея — усилить вес заголовка документа
  в эмбеддинге, поскольку именно заголовок отличает страницы-близнецы.

## Как воспроизвести

```bash
docker compose up -d                                  # база и приложение
docker compose --profile tools run --rm indexer       # индексация, ~2 часа
```

Затем `http://localhost:8000`. Метрики пересчитываются командами
`run_retrieval`, `run_generation` и `run_judge` — см. [README](../README.md).
