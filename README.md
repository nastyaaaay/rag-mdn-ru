# RAG по документации MDN с честной оценкой качества

Поиск и ответы по русской документации MDN (JavaScript, CSS, HTML, HTTP,
словарь веб-терминов) с измерением того, насколько ответы подтверждаются
документами, а насколько выдуманы моделью.

> **Статус: все 15 шагов пройдены.**
> Система работает целиком и запускается одной командой в Docker.
> Качество поиска и честность ответов измерены (см. ниже), включая
> проверку самой проверяющей модели. Ход работы с ошибками и тупиками —
> в [PLAN.md](PLAN.md). Здесь не появится ни одного обещания, которого
> не выполняет код.

## Зачем это

Собрать RAG-систему может каждый. Сказать, насколько она врёт, — почти никто.
Цель проекта — не «оно как-то отвечает», а отчёт с числами: сколько утверждений
подтверждается документами, как часто система признаётся, что ответа не знает,
и на каких вопросах она ошибается.

**Сводка результатов, включая то, что осталось несделанным** —
[reports/SUMMARY.md](reports/SUMMARY.md). Ход работы с ошибками и тупиками —
[PLAN.md](PLAN.md).

## Измеренная честность ответов

Главное в проекте. Все метрики ниже посчитаны **кодом, без участия языковой
модели**, поэтому воспроизводимы точно.

| Метрика | Значение |
|---|---:|
| Корректные отказы на ловушках | **60%** (6/10) |
| Ложные отказы | 7% (3/42) |
| **Выдуманные ссылки** | **0%** (0/52) |
| Точность цитирования | 67% (18/27) |

**Ссылки честные, содержание — не всегда.** Модель ни разу не сослалась на
несуществующий фрагмент, но это не значит, что она не выдумывает: она
добросовестно ссылается на реальный фрагмент и приписывает ему то, чего там
нет. Пример, найденный при ручной проверке:

> **Вопрос:** Чем отличается постоянное перенаправление 301 от временного?
> **Ответ:** «301 может изменять метод запроса на GET…» со ссылкой на фрагмент,
> который на самом деле про код **308**. В самих фрагментах написано, что метод
> на GET меняет **303**.

**Ловушки пробиваются предсказуемо.** Вопросы про темы, которых в корпусе нет
совсем, отклоняются надёжно. А там, где тема **мельком упоминается** в текстах
(`addEventListener` встречается 42 раза), модель достраивает ответ из
собственных знаний вопреки прямому запрету в промпте. Это конкретный
воспроизводимый механизм отказа, а не «иногда врёт».

Подробности с разбором каждого случая —
[reports/generation_report.md](reports/generation_report.md).

### Почему модели-судье нельзя верить на слово

Обоснованность ответов оценивала вторая языковая модель — и заодно
измерялось, насколько она сама попадает в цель:

| Что | Значение |
|---|---:|
| Обоснованность **по мнению судьи** | 94% |
| **Согласие судьи с независимой разметкой** | **63%** |
| Обоснованность **по разметке** | **74%** |

Из 19 размеченных ответов судья разошёлся с разметкой семь раз — и **все семь
в одну сторону**, в пользу системы. Ни разу не занизил.

Показательнее всего: судья одобрил **все четыре выдумки на ловушках**. Ответы
про `navigator.geolocation.getCurrentPosition()` и `getUserMedia()` — методы,
которых в корпусе нет вообще, — он счёл подтверждающимися.

Без этой проверки в отчёте стояло бы «обоснованность 94%», и она скрыла бы
ровно те случаи, ради поиска которых проект и делался. Метрики, посчитанные
кодом, оказались надёжнее оценки языковой модели.

## Измеренное качество поиска

Проверка на 52 вопросах, разбитых по типам. Полный отчёт с разбором каждого
промаха — [reports/retrieval_report.md](reports/retrieval_report.md).

| Способ поиска | Recall@1 | Recall@5 | MRR |
|---|---:|---:|---:|
| векторный | **43%** | 64% | **0.528** |
| векторный без фрагментов кода | 40% | **67%** | 0.521 |
| гибридный | 38% | 64% | 0.497 |
| полнотекстовый | 5% | 7% | 0.056 |

Два вывода, которые дались только измерением:

**Гибридный поиск оказался хуже чистого векторного.** Он стоял по умолчанию
из соображения «объединение двух способов усилит оба» — цифры это
опровергли. Полнотекстовый поиск слишком слаб на вопросах, заданных
человеческим языком, и в объединённой выдаче тянет результат вниз.

**Средняя цифра скрывает главное.** Recall@5 по группам вопросов:

| Тип вопроса | Recall@5 |
|---|---:|
| прямой, терминами документации | **93%** |
| требующий нескольких документов | 80% |
| заданный своими словами | 50% |
| **различение похожих страниц** | **30%** |

Последняя строка — реальная слабость системы, а не случайность: на вопрос
«какой метод массива отбирает элементы по условию» находятся `every`,
`some`, `includes`, но не `filter`. Система уверенно определяет тему
и не различает конкретные методы внутри неё, потому что тексты соседних
страниц справочника почти дословно совпадают.

## Стек

| Что | Чем |
|---|---|
| Язык | Python 3.12 |
| Веб | FastAPI |
| Векторная база | PostgreSQL 17 + pgvector |
| Эмбеддинги | fastembed, `multilingual-e5-large`, локально |
| Генерация | OpenAI-совместимый API; по умолчанию локальная Ollama |
| Запуск | Docker Compose |

Слой генерации не привязан к одному поставщику: он говорит на OpenAI-совместимом
протоколе, который понимают Ollama, OpenRouter, Groq и другие. По умолчанию
работает локальная модель, поэтому проект воспроизводится **без API-ключей
и без оплаты**. Переключение на облако — три строки в `.env`, код не меняется.

## Запуск

Нужен Python 3.12 или новее.

Создать окружение и поставить зависимости:

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Запустить тесты:

```bash
.venv\Scripts\python.exe -m pytest
```

Ожидаемый результат — все тесты проходят.

> На Windows виртуальное окружение намеренно **не активируется** через
> `Activate.ps1`: политика выполнения скриптов по умолчанию это запрещает.
> Вместо активации везде используется прямой путь `.venv\Scripts\python.exe` —
> так же надёжнее, пакеты гарантированно ставятся в нужное окружение.

## Загрузка корпуса и отчёт о его качестве

```bash
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.corpus.cli
```

Скачивает нужные разделы MDN (частичным `git clone`, без всего репозитория)
и строит отчёт [reports/corpus_report.md](reports/corpus_report.md): сколько
документов найдено, сколько исключено как непереведённые или как заглушки,
распределение доли кириллицы, список встречающихся макросов MDN. Из 1429
найденных документов в индекс проходит 1323 — как посчитан этот порог
и что было исправлено по пути, описано в [PLAN.md](PLAN.md), раздел «Данные».

## Проверка парсера

```bash
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.corpus.parse_all
```

Разбирает все отобранные документы и печатает сводку: сколько разобрано,
сколько ошибок, остались ли незнакомые макросы MDN. Команда завершается
с ненулевым кодом, если что-то пошло не так, — её можно ставить в CI.
Примеры разобранных документов сохраняются в
[reports/parsed_samples.md](reports/parsed_samples.md): это ровно тот текст,
который попадёт в поисковый индекс.

## Нарезка на фрагменты

```bash
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.corpus.chunk_all
```

Нарезает корпус на фрагменты и проверяет инварианты, которые невозможно
проверить юнит-тестами на придуманных данных: каждый фрагмент влезает
в лимит модели эмбеддингов, ни один блок кода не разорван пополам, пустых
фрагментов нет. Команда завершается с ненулевым кодом при любом нарушении.

1323 документа дают 7895 фрагментов. Примеры сохраняются в
[reports/chunk_samples.md](reports/chunk_samples.md) ровно в том виде,
в каком уйдут в модель.

Размеры фрагментов заданы в символах, но код считается с двойным весом:
измерение показало, что плотный код расходует лимит модели вдвое быстрее
прозы (1.8 символа на токен против 3.6). Без этой поправки один фрагмент
превышал лимит и молча обрезался моделью — подробности в [PLAN.md](PLAN.md).

## База данных

```bash
docker compose up -d
```

Поднимает PostgreSQL 17 с расширением pgvector. При первом запуске
автоматически создаётся схема из [db/init/01-schema.sql](db/init/01-schema.sql):
таблицы документов и фрагментов, векторный индекс HNSW и индекс
полнотекстового поиска с русской морфологией (нужен для честного сравнения
«векторный поиск против обычного» на шаге 12).

Остановить: `docker compose stop`. Удалить вместе с данными:
`docker compose down -v`.

Тесты, которым нужна база, помечены меткой `db`. Без поднятой базы они
**пропускаются, а не падают** — обычный `pytest` работает и на машине без
Docker. Запустить только их: `pytest -m db`.

## Индексация

```bash
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.index_all
```

Полный конвейер: отбор документов → парсер → нарезка → эмбеддинги → база.
Операция разовая и небыстрая (минуты), печатает прогресс и заканчивается
сводкой: сколько документов и фрагментов записано, сколько пропущено и
почему. Требует поднятой базы (`docker compose up -d`).

Индексация всегда полная: старые данные очищаются, иначе в базе смешались
бы фрагменты, посчитанные разными настройками. Параметры (модель, размерность,
размеры фрагментов, порог фильтра) записываются рядом с данными и сверяются
при поиске — расхождение остановит работу с внятным сообщением вместо того,
чтобы молча портить выдачу.

## Вопрос к системе

```bash
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.ask "Что возвращает метод filter у массива?"
```

Находит фрагменты и просит модель составить по ним ответ:

```
=== Ответ ===
Метод `filter()` создаёт новый массив со всеми элементами, прошедшими
проверку, задаваемую в передаваемой функции. [5]

Источники:
  https://developer.mozilla.org/ru/docs/Web/JavaScript/Reference/Global_Objects/Array/filter
```

На вопрос, ответа на который в документах нет, система обязана ответить
единственной фиксированной фразой — и отвечает:

```
> чем useState отличается от useEffect в React
=== Ответ ===
В предоставленных документах ответа нет.
```

Номер в квадратных скобках — ссылка на конкретный переданный фрагмент.
Это даёт проверку на выдумывание **без всякой модели-судьи**: если модель
сослалась на фрагмент номер 7, а ей передали пять, ссылка взята с потолка,
и программа сообщает об этом.

Ключ `--hits-only` показывает только найденные фрагменты, не обращаясь
к модели, — удобно, когда модель недоступна.

### Способы поиска

Способ задаётся ключом `--method`:

| Способ | Как ищет | Сильная сторона | Слабая |
|---|---|---|---|
| `vector` | по смыслу, через эмбеддинги | находит, даже если слова в вопросе другие | путает похожие страницы справочника |
| `fulltext` | по словам, с русской морфологией | точен, когда известен термин | бесполезен при вопросе «своими словами» |
| `hybrid` | объединяет оба | — | по метрикам проигрывает векторному |
| `vector_nocode` | векторный без фрагментов чистого кода | лучше на бытовых формулировках (+8 п.п.) | чуть хуже на первой позиции |

Ключ `--compare` покажет выдачу всех трёх рядом — удобно, чтобы увидеть
разницу своими глазами.

> **По умолчанию пока стоит `hybrid`, хотя измерение показало, что лучше
> `vector`** (43% против 38% по Recall@1). Значение по умолчанию будет
> изменено на шаге 12, где сравниваются и другие настройки — менять его
> отдельно, не проверив остальные варианты, значит принимать решение
> по одному числу.

## Оценка качества ответов

```bash
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.evaluation.run_generation
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.evaluation.run_judge
```

Первая команда отвечает на все 52 эталонных вопроса и считает метрики,
**не требующие языковой модели** — они воспроизводимы точно:

- доля корректных отказов на ловушках (главная метрика честности);
- доля ложных отказов — сдалась там, где ответ был;
- доля выдуманных ссылок — сослалась на фрагмент, которого не передавали;
- точность цитирования.

Вторая команда оценивает обоснованность моделью-судьёй и **отдельно
измеряет, насколько судье можно верить** — согласие с независимой
разметкой из `eval/judge_labels.json`. Без этого числа «обоснованность 85%»
была бы оценкой, взятой у модели на слово.

Отчёты: [reports/generation_report.md](reports/generation_report.md)
и [reports/judge_report.md](reports/judge_report.md).

## Оценка качества поиска

```bash
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.evaluation.run_retrieval
```

Прогоняет эталонный набор ([eval/golden_set.yaml](eval/golden_set.yaml),
52 вопроса) через все способы поиска и считает Recall@k и MRR **по каждой
группе вопросов отдельно**. Отчёт с разбором каждого промаха сохраняется
в [reports/retrieval_report.md](reports/retrieval_report.md).

Метрики считаются без участия языковой модели — сопоставляются только
найденные документы с эталонными. Поэтому цифры воспроизводимы: тот же
индекс всегда даёт тот же результат.

Ловушки (вопросы, ответа на которые в корпусе нет) в Recall не участвуют:
верного документа у них не существует, и засчитывать их как промахи
значило бы наказывать систему за правильное поведение. Их проверка —
отдельная метрика на шаге 11.

## Проверка эмбеддингов на реальной модели

```bash
set PYTHONPATH=src && .venv\Scripts\python.exe -m ragmdn.embeddings_check
```

При первом запуске скачивает модель `intfloat/multilingual-e5-large`
(~2.24 ГБ), затем проверяет: совпадает ли размерность вектора с настройками,
меняет ли что-то префикс `query:`/`passage:`, и — самое важное — различает
ли модель две почти одинаковые страницы справочника (`Math.acos()` и
`Math.asin()`, отличаются в тексте одним словом). Подробности и цифры —
в [PLAN.md](PLAN.md).

## Веб-интерфейс и HTTP-API

```bash
set PYTHONPATH=src && .venv\Scripts\uvicorn.exe ragmdn.api:app
```

Откройте `http://localhost:8000` — простая страница с полем для вопроса.
Автоматическая документация API — на `http://localhost:8000/docs`.

| Метод | Что делает |
|---|---|
| `POST /ask` | ищет и отвечает: текст, источники, признак отказа |
| `POST /search` | только поиск, **без обращения к модели** — работает, даже когда модель недоступна |
| `GET /health` | готовность: размер индекса, какие модели используются |

В ответе `/ask` есть поле `has_invalid_citation` — признак того, что модель
сослалась на несуществующий фрагмент. Клиент видит это сразу, а не узнаёт
из отчёта постфактум.

## Запуск целиком в Docker

```bash
docker compose up -d
```

Поднимает базу и приложение. Индексация вынесена в отдельный профиль,
потому что это разовая операция на час:

```bash
docker compose --profile tools run --rm indexer
```

Модель эмбеддингов (2.2 ГБ) намеренно **не входит в образ** — она
скачивается при первом запуске в отдельный том и переживает пересборку.
Иначе образ раздувался бы до трёх гигабайт и пересобирался при каждой
смене модели.
