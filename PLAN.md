# PLAN.md — RAG по документации MDN с честной оценкой качества

Дата составления: 2026-08-08.

---

## 1. Что делаем

Система, которая отвечает на вопросы по русской документации MDN
(JavaScript, CSS, HTML, HTTP и словарь веб-терминов), опираясь только на текст
документации, и **которая умеет доказать, насколько она права**.

Ключевая часть — не сам поиск, а измерение. На выходе должен быть отчёт,
где написано: столько-то ответов подтверждается документом, столько-то модель
придумала, вот на каких вопросах она врёт.

### Какие требования из вакансий закрывает

| Требование | Чем закрывается |
|---|---|
| RAG | вся система целиком |
| Эмбеддинги | fastembed, локальная модель |
| Векторная база | pgvector |
| PostgreSQL | pgvector живёт в Postgres; там же полнотекстовый поиск для сравнения |
| Docker | docker compose поднимает базу и приложение |
| Работа с API моделей | OpenAI-совместимый HTTP-клиент, провайдер переключается переменной окружения |

## 2. Решения и почему именно так

| Решение | Почему |
|---|---|
| Python 3.12 + FastAPI | стандарт для RAG; на собеседовании этого и ждут |
| PostgreSQL 17 + pgvector | одна база вместо двух: и векторы, и обычные таблицы, и полнотекстовый поиск |
| fastembed, `multilingual-e5-small` | локально, бесплатно, поддерживает русский, ставится как обычная библиотека |
| Ollama на хосте | бесплатно, без карты и геоблокировок; на RTX 3070 Ti работает быстро |
| OpenAI-совместимый слой | тот же код ходит и в Ollama, и в облако; Claude подключится одной переменной |
| Корпус: MDN на русском | CC-BY-SA 2.5 — свободная лицензия **без запрета коммерческого использования** |

### Про API моделей — честная формулировка для README

Мы не прибиваем код к одному вендору. Слой генерации говорит на
OpenAI-совместимом протоколе — его понимают Ollama, OpenRouter, Groq, GitHub Models.
По умолчанию работает локальная модель, поэтому проект воспроизводится без ключей
и без денег. Если задать `LLM_BASE_URL` и `LLM_API_KEY`, тот же код пойдёт в облако.

### Почему не learn.javascript.ru

Учебник Кантора отличный, но его лицензия — `CC-BY-NC`, названная самим автором
**отзывной и исключительной**, с прямой просьбой обращаться за разрешением на любое
использование, кроме чтения. Копия текстов в публичном портфельном репозитории
на таких условиях — ненужный риск. MDN отдаёт контент под CC-BY-SA 2.5 без оговорок.

## 3. Данные — посмотрели до того, как писать код

Источник: `github.com/mdn/translated-content`, папка `files/ru`, лицензия CC-BY-SA 2.5.
Формат — Markdown с YAML-заголовком. Один документ = один файл `index.md`.

Всего в `files/ru` — 2787 документов, 19.2 МБ текста.

### Что берём

| Раздел | Документов | Текста |
|---|---|---|
| `web/javascript` | 602 | 3.19 МБ |
| `web/css` | 350 | 2.12 МБ |
| `glossary` | 229 | 0.35 МБ |
| `web/html` | 127 | 1.36 МБ |
| `web/http` | 121 | 0.65 МБ |
| **Итого** | **1429** | **7.67 МБ** |

Не берём: `web/api` (868 документов — переведён плохо, см. ниже), `web/svg`,
`learn_web_development`, `mozilla`, `games`, `webassembly`, `mdn`,
а также `conflicting` и `orphaned` — служебные свалки самого MDN.

### Что в данных подозрительного

1. **Метка языка в пути к файлу врёт.** Файл лежит в `files/ru/`, но это ничего
   не гарантирует. Замерили долю кириллицы в прозе (код из подсчёта исключили)
   на случайной выборке из 14 документов — разброс **от 9% до 85%**:

   | Документ | Кириллица |
   |---|---|
   | `web/api/htmlelement/offsetheight` | 9% |
   | `web/api/gamepad_api/using_the_gamepad_api` | 13% |
   | `learn_web_development/core/scripting/event_bubbling` | 36% |
   | `web/javascript/reference/global_objects/date/tostring` | 63% |
   | `web/javascript/reference/operators/logical_and` | 82% |
   | `web/javascript/reference/global_objects/array/filter` | 85% |

   Web API — фактически английский текст в папке `ru`. JavaScript переведён прилично.
   **Решение:** считаем долю кириллицы для каждого документа и отсекаем по порогу.
   Порог выбираем по реальному распределению на шаге 2, а не на глаз.
   Число отсеянных документов идёт в README.

   Даже 85% — не признак плохого перевода: в документации много английских
   идентификаторов вне блоков кода (`undefined`, `Array`, `Content-Type`),
   и это нормальный русский технический текст.

2. **Макросы MDN в двойных фигурных скобках.** `{{JSRef}}`, `{{optional_inline}}`,
   `{{jsxref("undefined")}}`, `{{deprecated_inline}}`. Их **нельзя просто вырезать**:
   `{{jsxref("undefined")}}` несёт осмысленное слово, которое должно остаться в тексте.
   Правило: макросы с аргументом-строкой разворачиваем в эту строку, макросы-флаги удаляем.

3. **Списки определений в диалекте MDN.** Конструкция вида
   ``- `callback` `` и следом с отступом `- : Описание параметра`.
   Обычный парсер Markdown превратит это в кашу из вложенных списков.
   Нам нужен читаемый текст «`callback` — Описание параметра».

4. **YAML-заголовок с `title` и `slug`** — это подарок. `slug` даёт готовую ссылку
   на источник: `https://developer.mozilla.org/ru/docs/<slug>`. Ссылку на источник
   не надо конструировать и угадывать — она берётся из самих данных.
   **Проверить на шаге 2:** открыть 5 таких адресов и убедиться, что они живые.

5. **Огромный разброс размеров документов.** `glossary` — около 1.5 КБ,
   отдельные статьи по CSS и JS — десятки килобайт. Короткий документ целиком
   помещается в один фрагмент, длинный даёт десятки. Нарезка должна корректно
   работать на обоих краях, и это граничный случай для тестов.

6. **Много почти одинаковых страниц.** `Array.map`, `Array.filter`, `Array.forEach`,
   `Array.reduce` — структура и лексика совпадают почти дословно.
   Это **самое интересное для оценки качества**: поиск обязан отличить `filter` от `map`,
   и именно здесь обычные системы промахиваются. Такие вопросы обязательно
   попадут в эталонный набор отдельной группой.

7. **Блоки кода** — обычные тройные обратные кавычки. Проще, чем в AsciiDoc.
   Код остаётся в тексте фрагмента (иначе ответ бесполезен), но фрагмент
   никогда не состоит **только** из кода.

8. **Возможны страницы-заглушки** — файл есть, содержания нет. Проверим на шаге 2
   и отсечём по минимальной длине.

### Шаг 2 пройден: что показала загрузка 1429 документов

Отчёт: [reports/corpus_report.md](reports/corpus_report.md), построчные данные —
`reports/corpus_stats.csv` (не в репозитории, генерируется скриптом).

Первая версия измерения доли кириллицы (только код и инлайн-код исключены из
подсчёта) дала кривую картину: 180 документов ниже порога 50%. Проверка глазами
нашла три источника систематической ошибки — не в переводе, а в измерении:

1. **MathML-формулы.** 31 документ (28 из них — методы `Math.*`: `acos`,
   `asin`, `log2`...) содержит формулы вида `<math>...<annotation
   encoding="TeX">...` — десятки латинских тегов и LaTeX-команд на короткий
   абзац отличного русского текста. `Math.acos()` тянуло на 40%, хотя перевод
   полный. Эти страницы — важная часть корпуса: именно на них проверяется,
   отличает ли поиск `acos` от `asin` (см. раздел 5).
2. **Сырой HTML внутри markdown.** Таблицы совместимости браузеров и
   встроенные live-примеры (макрос `{{EmbedLiveSample}}`, 552 раза) содержат
   голые теги `<td>`, `<div>`, `<code>`, `<tr>` — они разметка, а не текст,
   но текст **внутри** тегов (например, `<td>Поддерживается</td>`) часто
   настоящая русская проза и должен остаться.
3. **Адреса markdown-ссылок.** `[текст](адрес)` — сам адрес обычно на
   латинице и не имеет отношения к переводу. Статья про `XMLHttpRequest`
   ссылалась на `peoplesofttutorial.com/difference-between-synchronous-and-
   asynchronous-messaging` — восемь английских слов из URL, не из текста
   статьи. Это оказался самый массовый источник ошибки: почти в каждой
   статье есть раздел «Смотрите также» со ссылками.

После трёх исправлений (функция переименована в `strip_markup`, поскольку
она чистит не только код) число исключённых по языку упало со 180 до **99**
— почти вдвое, притом за счёт устранения ошибки измерения, а не ослабления
критерия. Каждое исправление — с тестом-регрессией на реальном найденном
случае (`tests/test_text_stats.py`).

Проверка глазами обоих краёв распределения:

- **Низ (0–10%, 15 документов)** — подтверждён как настоящий непереведённый
  текст: например, `border-image-outset` — заголовки разделов переведены
  шаблоном («Синтаксис», «Значения»), а сам текст статьи полностью на
  английском. Фильтр не ошибается.
- **Граница 40–50%** — смешанная зона. `Symbol.replace` (42%) — короткая, но
  **полностью** переведённая статья: мало прозы, много вызовов
  `{{jsxref(...)}}` с английскими именами методов в аргументах (это
  нормально, имена методов не переводятся). А документы `base64` (28%) и
  `writing-mode` (29%) — уже настоящий брак перевода: английская фраза
  прямо посреди русского предложения, необработанный заголовок `## Summary`.
  Значит, метод в целом верно различает «мало текста» и «плохой перевод»,
  но не идеально на стыке.

**Решение: порог оставлен на 50%.** Он консервативен — теряет немного
коротких, но полностью переведённых справочных страниц вроде
`Symbol.replace`. Это осознанный компромисс: для проекта, который меряет
честность ответов, важнее не пустить в индекс документ с неполным переводом,
чем не потерять единичные короткие статьи.

Заглушек (короче 200 символов) — 7, все в `glossary`, отсеяны отдельно от
языкового фильтра.

Живые адреса: 5 URL, собранных из поля `slug`, проверены — все отвечают 200.

Полный список макросов: 74 разных, топ-30 — в отчёте. Самые частые:
`{{jsxref}}` (4286), `{{cssxref}}` (2222), `{{HTMLElement}}` (1946),
`{{Compat}}` (965), `{{Specifications}}` (912) — все ожидаемые, разбираются
на шаге 3.

### Шаг 3 пройден: парсер

Пример результата — [reports/parsed_samples.md](reports/parsed_samples.md),
три разобранных документа целиком, как они попадут в индекс.

Прогон по всем 1323 документам: **0 ошибок разбора, 0 неизвестных макросов,
0 пустых документов**. Классификация всех 45 макросов оказалась полной.

Что пришлось учесть:

1. **Порядок обработки.** Блоки кода прячутся под заглушки **до** всей
   остальной чистки. Иначе `<div>` в примере кода (нужен читателю) не отличить
   от `<div>` в разметке статьи (мусор), а `{{ user.name }}` в шаблонном
   примере был бы принят за макрос MDN.
2. **Подпись ссылки бывает русской.** У двухаргументных макросов второй
   аргумент — видимый текст: `{{Glossary("computer programming",
   "программировании")}}`. Берём **последний** аргумент; взяли бы первый —
   выкинули бы русское слово из предложения и заменили английским адресом.
3. **Кавычки бывают и одинарные**: `{{HTTPHeader('Date')}}`.
4. **Скобки внутри аргумента**: `{{jsxref("Statements/if...else",
   "if (condition)")}}` — разбор не должен обрываться на первой `)`.
5. **Адреса markdown-ссылок убраны, текст оставлен.** Путь
   `/ru/docs/Learn_web_development/Core/Scripting/Network_requests` —
   это десяток английских слов, которых читатель на странице не видит.
6. **Списки определений склеены.** В MDN параметры записаны двумя строками
   (термин, затем `- : описание`); в плоском тексте они выглядели бы как
   два несвязанных пункта. Стало: «`callbackFn` — Функция-предикат…».
7. **Пометки переведены в текст:** `{{optional_inline}}` →
   «(необязательный)», `{{deprecated_inline}}` → «(устаревшая возможность)».
   Это полезно для поиска: вопрос «что устарело» теперь что-то находит.

Заодно исправлена ошибка измерения из шага 2: регэксп имени макроса
обрезался на дефисе, из-за чего в отчёте фигурировал несуществующий
макрос `{{non}}` (80 раз) вместо `{{non-standard_inline}}` (66) и
`{{non-standard_header}}` (13).

### Что это означает для шага 4 (нарезка)

Замеры по 8242 разделам:

| Показатель | Значение |
|---|---|
| Длина раздела: медиана | 254 символа |
| Длина раздела: 75-й процентиль | 579 символов |
| Длина раздела: максимум | **70 327 символов** |
| Разделов длиннее 2000 символов | 317 |
| Разделов короче 30 символов | **688** |

Из этого следует, что нарезка должна работать **в обе стороны**, а не только
резать длинное:

- **Склеивать короткое.** 688 разделов короче 30 символов — это «Смотрите
  также» со списком ссылок и «Тип ошибки» с единственным словом `TypeError`.
  По отдельности как фрагменты бесполезны, но осмысленны вместе с путём
  заголовков и соседним текстом.
- **Резать длинное.** Один раздел в `Web/HTML/Reference/Elements` — 70 тысяч
  символов (справочная таблица всех HTML-элементов).
- **Не оставлять фрагменты из одного кода.** Раздел «Синтаксис» у
  `Array.prototype.filter()` состоит только из примера кода — к нему надо
  присоединять окружающий текст, иначе фрагмент не найдётся по смыслу.

### Известное ограничение фильтра по языку

Доля кириллицы (шаг 2) считается по сырому тексту, **до** разворачивания
макросов. У документов с большим числом ссылок вида
`{{Glossary("Accessibility", "доступностью")}}` в подсчёт попадает и
английский адрес, и русская подпись, хотя читатель видит только вторую.
То есть оценка слегка занижена, и фильтр чуть строже, чем задумано.
Пересчёт метрики на разобранном тексте — возможное улучшение; порог 50%
выбран консервативно и с этим запасом.

## 4. Архитектура

```
Загрузка .md → Фильтр по языку → Парсер Markdown → Нарезка → Эмбеддинги
                                                                  ↓
Вопрос → эмбеддинг → поиск в pgvector → топ-k → промпт → LLM → ответ + ссылки
                                          ↓
                                 Модуль оценки → отчёт о качестве
```

### Схема базы

```
documents  — один документ MDN
  id, source_path, slug, title, area (javascript/css/html/http/glossary),
  source_url, cyrillic_ratio, char_count

chunks     — фрагмент текста
  id, document_id, ord, heading_path, content,
  char_count, content_hash, embedding vector(384)

  индекс HNSW по embedding (косинусное расстояние)
  индекс GIN по to_tsvector('russian', content) — для полнотекстового поиска
```

`heading_path` — «JavaScript › Array.prototype.filter() › Описание».
Он добавляется в начало текста перед вычислением эмбеддинга. Без этого фрагмент
«Метод вызывает функцию один раз для каждого элемента» не отличить от десятка
таких же фрагментов из соседних страниц — а мы уже знаем, что таких страниц много.

### Грабли, о которых легко забыть

Модель e5 требует префиксов: тексты кодируются как `passage: ...`,
а запросы как `query: ...`. Если перепутать или забыть — качество поиска
молча просядет, и никакой ошибки не будет. Пишем тест.

## 5. Как измеряем качество — это главное

Две группы метрик. Первая считается **без всякой LLM**, детерминированно
и воспроизводимо. Вторая требует модель-судью, и её надёжность мы тоже проверим.

### Группа A. Качество поиска (без LLM)

Эталонный набор: вопрос → идентификатор документа, где лежит ответ.

- **Recall@k** — в какой доле случаев нужный документ попал в первые k результатов (k = 1, 3, 5, 10).
- **MRR@10** — насколько высоко он стоит в выдаче.

Считаем не только в целом, но и **по группам вопросов** (см. ниже).
Эти числа не зависят от настроения модели и одинаковы при каждом прогоне.

### Группа B. Качество ответа

- **Обоснованность.** Модель-судья разбивает ответ на отдельные утверждения
  и проверяет каждое против найденных фрагментов. Метрика — доля подтверждённых
  утверждений. Это и есть «сколько модель выдумала».
- **Полнота.** Отвечает ли ответ на вопрос по существу, а не отписка.
- **Точность цитирования.** Источник из ответа действительно входит в переданные
  фрагменты и действительно содержит утверждение.
- **Доля корректных отказов** на вопросах-ловушках.

### Из чего состоит эталонный набор

Около 50 вопросов, разбитых на группы — метрики считаем по каждой отдельно:

| Группа | Сколько | Зачем |
|---|---|---|
| Прямые вопросы по документации | ~15 | базовый уровень |
| Вопросы «как спросил бы человек» | ~12 | «почему у меня блок не центрируется?» вместо «свойство justify-content» |
| **Различение похожих страниц** | ~10 | `filter` против `map`, `let` против `const` — здесь ломается большинство систем |
| **Ловушки** | ~10 | правдоподобные вопросы про веб, ответа на которые в корпусе нет |
| Вопросы на стыке тем | ~5 | ответ требует и CSS, и HTML |

### Вопросы-ловушки

Правильное поведение — «в предоставленных документах ответа нет».
Ловушки делаем правдоподобными: про веб-разработку, но про то, чего в нашем
корпусе нет — например, про Web API, который мы сознательно исключили.
Это честнее, чем спрашивать про кулинарию.

### Сравнение с базовыми вариантами

Одни и те же вопросы прогоняем через:

1. **Без RAG** — модель отвечает по памяти.
2. **Полнотекстовый поиск Postgres** — без эмбеддингов, по словам.
3. **Векторный поиск** — наша основная схема.
4. **Гибрид** — объединение двух предыдущих.

Плюс сравнение 2–3 размеров фрагмента. Выбор обосновываем числами, а не на глаз.

### Проверка самого судьи

Слабая локальная модель может судить плохо. Берём 20 ответов, размечаем вручную,
сравниваем с вердиктом судьи, считаем процент совпадения. Публикуем это число
в README — тогда все остальные цифры читаются с честной поправкой.

### Как собираем эталонный набор

Черновик генерируем моделью по документам, **затем проверяем глазами каждый вопрос**
и правим. Вопросы группы «как спросил бы человек» формулируем сами — модель
неизбежно перескажет документ его же словами, и метрики окажутся завышенными.
В README пишем честно: собран полуавтоматически, вычитан вручную. Хранится в YAML.

## 7. Что может пойти не так

| Риск | Насколько вероятно | Что делаем |
|---|---|---|
| Docker Desktop не встанет: нужна виртуализация в BIOS и WSL2 | Средне | Разбираем ошибку вместе. Запасной вариант — Postgres в WSL, но теряем требование Docker, поэтому боремся |
| Кончится место на C: (свободно 15 ГБ) | Высоко без подготовки | Данные Docker и модели Ollama сразу на диск D: |
| Порог фильтра по языку выбран произвольно | Средне | Смотрим распределение и обосновываем; число отсеянных — в README |
| Незнакомый макрос `{{...}}` испортил текст | Средне | Собираем полный список макросов на шаге 2, неизвестные — в лог |
| Забыли префиксы `query:` / `passage:` для e5 | Легко пропустить | Отдельный тест |
| Похожие страницы не различаются поиском | **Высоко** | Ради этого и добавлен `heading_path` в эмбеддинг; если не поможет — гибридный поиск |
| Фрагмент разрывает блок кода пополам | Средне | Правило нарезки: блок кода не разрывается |
| Судья-модель судит плохо | Высоко | Измеряем согласие судьи с человеком и публикуем это число |
| Модель в Ollama не влезет в 8 ГБ видеопамяти | Низко | Берём 7–8 млрд параметров в квантованном виде |
| В репозиторий утечёт `.env` | Низко, но дорого | `.gitignore` с первого коммита, проверка перед каждым коммитом |
| Эталонный набор подогнан под нашу же систему | Средне | Вопросы формулируем по тексту документации, а не по выдаче поиска |
| Корпус в 1429 документов долго индексируется | Низко | Разовая операция; засекаем время и пишем его в README |

## 8. Само-ревью плана: где он слабый

1. **Эталонный набор, сгенерированный моделью, будет слишком лёгким.**
   Модель сформулирует вопрос словами самого документа, поиск найдёт его тривиально.
   *Исправление:* выделены отдельные группы вопросов, метрики считаем по каждой.

2. **Ответ может лежать сразу в нескольких документах.**
   *Исправление:* в эталоне допускаем список приемлемых документов.

3. **Не задан размер фрагмента.** *Исправление:* шаг 12 сравнивает 2–3 размера,
   выбор обосновываем числами.

4. **Обоснованность и полезность — не одно и то же.** Ответ «в документации
   упоминается метод filter» идеально обоснован и бесполезен. Если мерить только
   обоснованность, система научится жульничать в сторону осторожности.
   *Исправление:* меряем ещё и полноту.

5. **Ловушки могут оказаться слишком очевидными.** *Исправление:* спрашиваем
   про Web API, который мы сознательно исключили из корпуса — тема близкая
   и правдоподобная.

6. **Один прогон — не результат.** *Исправление:* температура 0, фиксируем версии
   модели, на итоговом прогоне 3 повтора с указанием разброса.

7. **Шаг 0 — стена в самом начале.** *Исправление:* шаги 2–4 не требуют ни Docker,
   ни Ollama. Если Docker закапризничает, работаем дальше, а его чиним параллельно.

8. **Фильтр по кириллице — грубый инструмент.** Он отсечёт и добротные короткие
   документы, где много идентификаторов. *Исправление:* порог подбираем по реальному
   распределению, проверяем глазами 10 документов у самой границы, и в README пишем,
   что метод грубый и почему выбран именно он.
