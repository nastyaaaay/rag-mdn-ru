# PLAN.md — RAG по документации MDN с честной оценкой качества

Статус: план на согласовании. Код ещё не писали.
Дата составления: 2026-08-08.

---

## 1. Что делаем

Система, которая отвечает на вопросы по русской документации MDN
(JavaScript, CSS, HTML, HTTP и словарь веб-терминов), опираясь только на текст
документации, и **которая умеет доказать, насколько она права**.

Ключевая часть — не сам поиск, а измерение. На выходе должен быть отчёт,
где написано: столько-то ответов подтверждается документом, столько-то модель
придумала, вот на каких вопросах она врёт.

### Какие требования из вакансий закрывает

| Требование | Чем закрывается |
|---|---|
| RAG | вся система целиком |
| Эмбеддинги | fastembed, локальная модель |
| Векторная база | pgvector |
| PostgreSQL | pgvector живёт в Postgres; там же полнотекстовый поиск для сравнения |
| Docker | docker compose поднимает базу и приложение |
| Работа с API моделей | OpenAI-совместимый HTTP-клиент, провайдер переключается переменной окружения |

## 2. Решения и почему именно так

| Решение | Почему |
|---|---|
| Python 3.12 + FastAPI | стандарт для RAG; на собеседовании этого и ждут |
| PostgreSQL 17 + pgvector | одна база вместо двух: и векторы, и обычные таблицы, и полнотекстовый поиск |
| fastembed, `multilingual-e5-large` | локально, бесплатно, поддерживает русский, ставится как обычная библиотека (изначально планировалась `-small`, но fastembed её не поддерживает — подробности в разделе 3) |
| Ollama на хосте | бесплатно, без карты и геоблокировок; на RTX 3070 Ti работает быстро |
| OpenAI-совместимый слой | тот же код ходит и в Ollama, и в облако; Claude подключится одной переменной |
| Корпус: MDN на русском | CC-BY-SA 2.5 — свободная лицензия **без запрета коммерческого использования** |

### Про API моделей — честная формулировка для README

Мы не прибиваем код к одному вендору. Слой генерации говорит на
OpenAI-совместимом протоколе — его понимают Ollama, OpenRouter, Groq, GitHub Models.
По умолчанию работает локальная модель, поэтому проект воспроизводится без ключей
и без денег. Если задать `LLM_BASE_URL` и `LLM_API_KEY`, тот же код пойдёт в облако.

### Почему не learn.javascript.ru

Учебник Кантора отличный, но его лицензия — `CC-BY-NC`, названная самим автором
**отзывной и исключительной**, с прямой просьбой обращаться за разрешением на любое
использование, кроме чтения. Копия текстов в публичном портфельном репозитории
на таких условиях — ненужный риск. MDN отдаёт контент под CC-BY-SA 2.5 без оговорок.

## 3. Данные — посмотрели до того, как писать код

Источник: `github.com/mdn/translated-content`, папка `files/ru`, лицензия CC-BY-SA 2.5.
Формат — Markdown с YAML-заголовком. Один документ = один файл `index.md`.

Всего в `files/ru` — 2787 документов, 19.2 МБ текста.

### Что берём

| Раздел | Документов | Текста |
|---|---|---|
| `web/javascript` | 602 | 3.19 МБ |
| `web/css` | 350 | 2.12 МБ |
| `glossary` | 229 | 0.35 МБ |
| `web/html` | 127 | 1.36 МБ |
| `web/http` | 121 | 0.65 МБ |
| **Итого** | **1429** | **7.67 МБ** |

Не берём: `web/api` (868 документов — переведён плохо, см. ниже), `web/svg`,
`learn_web_development`, `mozilla`, `games`, `webassembly`, `mdn`,
а также `conflicting` и `orphaned` — служебные свалки самого MDN.

### Что в данных подозрительного

1. **Метка языка в пути к файлу врёт.** Файл лежит в `files/ru/`, но это ничего
   не гарантирует. Замерили долю кириллицы в прозе (код из подсчёта исключили)
   на случайной выборке из 14 документов — разброс **от 9% до 85%**:

   | Документ | Кириллица |
   |---|---|
   | `web/api/htmlelement/offsetheight` | 9% |
   | `web/api/gamepad_api/using_the_gamepad_api` | 13% |
   | `learn_web_development/core/scripting/event_bubbling` | 36% |
   | `web/javascript/reference/global_objects/date/tostring` | 63% |
   | `web/javascript/reference/operators/logical_and` | 82% |
   | `web/javascript/reference/global_objects/array/filter` | 85% |

   Web API — фактически английский текст в папке `ru`. JavaScript переведён прилично.
   **Решение:** считаем долю кириллицы для каждого документа и отсекаем по порогу.
   Порог выбираем по реальному распределению на шаге 2, а не на глаз.
   Число отсеянных документов идёт в README.

   Даже 85% — не признак плохого перевода: в документации много английских
   идентификаторов вне блоков кода (`undefined`, `Array`, `Content-Type`),
   и это нормальный русский технический текст.

2. **Макросы MDN в двойных фигурных скобках.** `{{JSRef}}`, `{{optional_inline}}`,
   `{{jsxref("undefined")}}`, `{{deprecated_inline}}`. Их **нельзя просто вырезать**:
   `{{jsxref("undefined")}}` несёт осмысленное слово, которое должно остаться в тексте.
   Правило: макросы с аргументом-строкой разворачиваем в эту строку, макросы-флаги удаляем.

3. **Списки определений в диалекте MDN.** Конструкция вида
   ``- `callback` `` и следом с отступом `- : Описание параметра`.
   Обычный парсер Markdown превратит это в кашу из вложенных списков.
   Нам нужен читаемый текст «`callback` — Описание параметра».

4. **YAML-заголовок с `title` и `slug`** — это подарок. `slug` даёт готовую ссылку
   на источник: `https://developer.mozilla.org/ru/docs/<slug>`. Ссылку на источник
   не надо конструировать и угадывать — она берётся из самих данных.
   **Проверить на шаге 2:** открыть 5 таких адресов и убедиться, что они живые.

5. **Огромный разброс размеров документов.** `glossary` — около 1.5 КБ,
   отдельные статьи по CSS и JS — десятки килобайт. Короткий документ целиком
   помещается в один фрагмент, длинный даёт десятки. Нарезка должна корректно
   работать на обоих краях, и это граничный случай для тестов.

6. **Много почти одинаковых страниц.** `Array.map`, `Array.filter`, `Array.forEach`,
   `Array.reduce` — структура и лексика совпадают почти дословно.
   Это **самое интересное для оценки качества**: поиск обязан отличить `filter` от `map`,
   и именно здесь обычные системы промахиваются. Такие вопросы обязательно
   попадут в эталонный набор отдельной группой.

7. **Блоки кода** — обычные тройные обратные кавычки. Проще, чем в AsciiDoc.
   Код остаётся в тексте фрагмента (иначе ответ бесполезен), но фрагмент
   никогда не состоит **только** из кода.

8. **Возможны страницы-заглушки** — файл есть, содержания нет. Проверим на шаге 2
   и отсечём по минимальной длине.

### Шаг 2 пройден: что показала загрузка 1429 документов

Отчёт: [reports/corpus_report.md](reports/corpus_report.md), построчные данные —
`reports/corpus_stats.csv` (не в репозитории, генерируется скриптом).

Первая версия измерения доли кириллицы (только код и инлайн-код исключены из
подсчёта) дала кривую картину: 180 документов ниже порога 50%. Проверка глазами
нашла три источника систематической ошибки — не в переводе, а в измерении:

1. **MathML-формулы.** 31 документ (28 из них — методы `Math.*`: `acos`,
   `asin`, `log2`...) содержит формулы вида `<math>...<annotation
   encoding="TeX">...` — десятки латинских тегов и LaTeX-команд на короткий
   абзац отличного русского текста. `Math.acos()` тянуло на 40%, хотя перевод
   полный. Эти страницы — важная часть корпуса: именно на них проверяется,
   отличает ли поиск `acos` от `asin` (см. раздел 5).
2. **Сырой HTML внутри markdown.** Таблицы совместимости браузеров и
   встроенные live-примеры (макрос `{{EmbedLiveSample}}`, 552 раза) содержат
   голые теги `<td>`, `<div>`, `<code>`, `<tr>` — они разметка, а не текст,
   но текст **внутри** тегов (например, `<td>Поддерживается</td>`) часто
   настоящая русская проза и должен остаться.
3. **Адреса markdown-ссылок.** `[текст](адрес)` — сам адрес обычно на
   латинице и не имеет отношения к переводу. Статья про `XMLHttpRequest`
   ссылалась на `peoplesofttutorial.com/difference-between-synchronous-and-
   asynchronous-messaging` — восемь английских слов из URL, не из текста
   статьи. Это оказался самый массовый источник ошибки: почти в каждой
   статье есть раздел «Смотрите также» со ссылками.

После трёх исправлений (функция переименована в `strip_markup`, поскольку
она чистит не только код) число исключённых по языку упало со 180 до **99**
— почти вдвое, притом за счёт устранения ошибки измерения, а не ослабления
критерия. Каждое исправление — с тестом-регрессией на реальном найденном
случае (`tests/test_text_stats.py`).

Проверка глазами обоих краёв распределения:

- **Низ (0–10%, 15 документов)** — подтверждён как настоящий непереведённый
  текст: например, `border-image-outset` — заголовки разделов переведены
  шаблоном («Синтаксис», «Значения»), а сам текст статьи полностью на
  английском. Фильтр не ошибается.
- **Граница 40–50%** — смешанная зона. `Symbol.replace` (42%) — короткая, но
  **полностью** переведённая статья: мало прозы, много вызовов
  `{{jsxref(...)}}` с английскими именами методов в аргументах (это
  нормально, имена методов не переводятся). А документы `base64` (28%) и
  `writing-mode` (29%) — уже настоящий брак перевода: английская фраза
  прямо посреди русского предложения, необработанный заголовок `## Summary`.
  Значит, метод в целом верно различает «мало текста» и «плохой перевод»,
  но не идеально на стыке.

**Решение: порог оставлен на 50%.** Он консервативен — теряет немного
коротких, но полностью переведённых справочных страниц вроде
`Symbol.replace`. Это осознанный компромисс: для проекта, который меряет
честность ответов, важнее не пустить в индекс документ с неполным переводом,
чем не потерять единичные короткие статьи.

Заглушек (короче 200 символов) — 7, все в `glossary`, отсеяны отдельно от
языкового фильтра.

Живые адреса: 5 URL, собранных из поля `slug`, проверены — все отвечают 200.

Полный список макросов: 74 разных, топ-30 — в отчёте. Самые частые:
`{{jsxref}}` (4286), `{{cssxref}}` (2222), `{{HTMLElement}}` (1946),
`{{Compat}}` (965), `{{Specifications}}` (912) — все ожидаемые, разбираются
на шаге 3.

### Шаг 3 пройден: парсер

Пример результата — [reports/parsed_samples.md](reports/parsed_samples.md),
три разобранных документа целиком, как они попадут в индекс.

Прогон по всем 1323 документам: **0 ошибок разбора, 0 неизвестных макросов,
0 пустых документов**. Классификация всех 45 макросов оказалась полной.

Что пришлось учесть:

1. **Порядок обработки.** Блоки кода прячутся под заглушки **до** всей
   остальной чистки. Иначе `<div>` в примере кода (нужен читателю) не отличить
   от `<div>` в разметке статьи (мусор), а `{{ user.name }}` в шаблонном
   примере был бы принят за макрос MDN.
2. **Подпись ссылки бывает русской.** У двухаргументных макросов второй
   аргумент — видимый текст: `{{Glossary("computer programming",
   "программировании")}}`. Берём **последний** аргумент; взяли бы первый —
   выкинули бы русское слово из предложения и заменили английским адресом.
3. **Кавычки бывают и одинарные**: `{{HTTPHeader('Date')}}`.
4. **Скобки внутри аргумента**: `{{jsxref("Statements/if...else",
   "if (condition)")}}` — разбор не должен обрываться на первой `)`.
5. **Адреса markdown-ссылок убраны, текст оставлен.** Путь
   `/ru/docs/Learn_web_development/Core/Scripting/Network_requests` —
   это десяток английских слов, которых читатель на странице не видит.
6. **Списки определений склеены.** В MDN параметры записаны двумя строками
   (термин, затем `- : описание`); в плоском тексте они выглядели бы как
   два несвязанных пункта. Стало: «`callbackFn` — Функция-предикат…».
7. **Пометки переведены в текст:** `{{optional_inline}}` →
   «(необязательный)», `{{deprecated_inline}}` → «(устаревшая возможность)».
   Это полезно для поиска: вопрос «что устарело» теперь что-то находит.

Заодно исправлена ошибка измерения из шага 2: регэксп имени макроса
обрезался на дефисе, из-за чего в отчёте фигурировал несуществующий
макрос `{{non}}` (80 раз) вместо `{{non-standard_inline}}` (66) и
`{{non-standard_header}}` (13).

### Что это означает для шага 4 (нарезка)

Замеры по 8242 разделам:

| Показатель | Значение |
|---|---|
| Длина раздела: медиана | 254 символа |
| Длина раздела: 75-й процентиль | 579 символов |
| Длина раздела: максимум | **70 327 символов** |
| Разделов длиннее 2000 символов | 317 |
| Разделов короче 30 символов | **688** |

Из этого следует, что нарезка должна работать **в обе стороны**, а не только
резать длинное:

- **Склеивать короткое.** 688 разделов короче 30 символов — это «Смотрите
  также» со списком ссылок и «Тип ошибки» с единственным словом `TypeError`.
  По отдельности как фрагменты бесполезны, но осмысленны вместе с путём
  заголовков и соседним текстом.
- **Резать длинное.** Один раздел в `Web/HTML/Reference/Elements` — 70 тысяч
  символов (справочная таблица всех HTML-элементов).
- **Не оставлять фрагменты из одного кода.** Раздел «Синтаксис» у
  `Array.prototype.filter()` состоит только из примера кода — к нему надо
  присоединять окружающий текст, иначе фрагмент не найдётся по смыслу.

### Шаг 4 пройден: нарезка на фрагменты

Пример результата — [reports/chunk_samples.md](reports/chunk_samples.md).
Проверка инвариантов на всём корпусе — команда `chunk_all`.

**Итог: 1323 документа → 6765 фрагментов**, медиана 591 символ.

Инварианты, проверенные на всех фрагментах (0 нарушений):

| Инвариант | Почему важен |
|---|---|
| Фрагмент влезает в лимит модели | сверх лимита текст обрезается **молча**, без ошибки |
| Блок кода не разорван | половина примера бесполезна и ядовита для эмбеддинга |
| Нет пустых фрагментов | искать в них нечего, а место занимают |

Что нашлось только на полном прогоне, а не в тестах:

1. **Резка длинного примера кода теряла ограждения.** Куски получались
   с непарными ` ``` `: начало примера выглядело как код, а хвост — как
   проза. 151 фрагмент из 6579. Теперь каждый кусок заново оборачивается
   в ограждения с тем же языком.
2. **Фрагмент из одних пробелов.** Ровно один, но в индексе ему делать нечего.
3. **Висячее ограждение из-за нестандартной разметки в исходнике.**
   Один случай на 6579. Гоняться за конкретным файлом смысла нет — данные
   и дальше будут подкидывать сюрпризы, поэтому парность ограждений
   теперь обеспечивается явно, а не надеждой на аккуратность MDN.
4. **Путь заголовков тратит тот же лимит, что и текст.** Изначально бюджет
   считался только по тексту, и `embedding_input` доходил до 1343 символов —
   это около 537 токенов при лимите модели 512. Самые длинные фрагменты
   молча обрезались бы. Теперь бюджет уменьшается на длину заголовка,
   и максимум ровно 1200 символов.

Осознанно принятые компромиссы (не ошибки):

- **213 фрагментов (3.1%) состоят только из кода.** Это длинные примеры,
  которые физически не помещаются вместе с прозой в лимит. Они не потеряны:
  `embedding_input` начинается с пути заголовков, поэтому фрагмент находится
  по запросу вида «пример filter».
- **268 фрагментов (4.0%) короче минимума.** Склейка с соседом сделала бы
  их сверхлимитными — лучше короткий фрагмент, чем обрезанный.

### Эмбеддинги: модель пришлось сменить, но замер подтвердил план

Изначально в конфиге стояла `intfloat/multilingual-e5-small`. При установке
`fastembed` выяснилось: библиотека конвертирует в ONNX не весь HuggingFace,
а свой список моделей, и `-small` версии E5 в нём нет. Из подходящих для
русского языка — `intfloat/multilingual-e5-large`: та же схема с префиксами
`query:`/`passage:`, тот же принцип, только больше (2.24 ГБ, 1024 измерения
вместо 384). Проверено командой `pip index versions fastembed` — установлена
последняя версия, это не вопрос обновления.

**Защита от главной грабли этой модели** (перепутать или забыть префикс —
модель не выдаст ошибку, просто молча посчитает похуже) сделана на уровне
интерфейса: `embeddings.py` не даёт вызывающему коду доступа к сырому тексту
без префикса — только `embed_passages()` и `embed_query()`, и каждый сам
решает, какой префикс нужен.

Три проверки на настоящей модели (`python -m ragmdn.embeddings_check`,
скачивает модель при первом запуске):

1. Размерность вектора — 1024, совпадает с настройками.
2. Один и тот же текст как `query:` и как `passage:` даёт разные векторы
   (похожесть 0.887, не 1.0) — префикс действительно на что-то влияет.
3. **Главная проверка: различает ли модель `Math.acos()` и `Math.asin()`** —
   две страницы справочника, отличающиеся в тексте одним словом. Взяты
   настоящие описания из корпуса и два вопроса, отличающиеся тем же словом:

   | Вопрос | acos | asin | Результат |
   |---|---:|---:|---|
   | «арккосинус числа» | **0.8401** | 0.8262 | ближе acos — верно |
   | «арксинус числа» | 0.8213 | **0.8360** | ближе asin — верно |

   Обе проверки прошли. Это прямой ответ на риск, отмеченный в разделе 5:
   «похожие страницы справочника — самое слабое место обычного поиска».
   Пока рано делать вывод про всю систему (это одна пара страниц и два
   вопроса, не полноценная метрика), но для выбора модели — обнадёживающе,
   и подтверждает решение оставить эти близнецы (`Math.*`) в эталонном
   наборе вопросов на шаге 8.

Побочная находка: fastembed предупреждает, что для e5-large схема
агрегации векторов внутри модели («mean pooling» вместо «CLS embedding»)
менялась между версиями библиотеки. Не стали фиксировать старую версию —
результат на реальных данных (таблица выше) правильный, эмпирика важнее
версии библиотеки.

### Шаг 5 пройден: PostgreSQL + pgvector

Поднимается одной командой `docker compose up -d`. Схема создаётся сама при
первом запуске, версия pgvector — 0.8.6.

**Главное решение шага — защита от рассинхрона индекса и кода.** Если базу
построить одной моделью эмбеддингов, а вектор запроса считать другой, поиск
**не сломается с ошибкой**: он продолжит работать и выдавать правдоподобную
чепуху. Обнаружить это можно только по испорченным метрикам, и не сразу.
Поэтому параметры индексации (модель, размерность, размеры фрагментов, порог
фильтра) пишутся в таблицу `index_meta` и сверяются перед поиском — при
расхождении работа останавливается с перечнем отличий.

Та же логика в `insert_chunks`: число фрагментов обязано совпадать с числом
векторов. Рассинхрон означал бы, что тексту приписан чужой вектор — самая
опасная из возможных ошибок, потому что она тоже ничего не ломает явно.

Что всплыло по ходу:

1. **`LANG: ru_RU.utf8` в compose ломает контейнер.** Русской локали в образе
   нет, `initdb` падает, контейнер уходит в бесконечный перезапуск. Локаль
   убрана: полнотекстовому поиску она не нужна, конфигурация `russian` живёт
   внутри PostgreSQL. Проверено: «создаёт» → основа «созда», морфология
   работает.
2. **Без таймаута подключения тесты висят.** При остановленной базе прогон
   растягивался на минуту вместо честного пропуска. Добавлен
   `db_connect_timeout`, а проверка доступности вынесена в session-фикстуру —
   одна попытка на весь прогон вместо одной на тест. Прогон без базы:
   6 секунд вместо 61.
3. **Размерность вектора продублирована** в SQL-схеме и в настройках Python —
   убрать дублирование нельзя, SQL не читает конфигурацию Python. Написан
   тест, который читает схему регулярным выражением и падает, если значения
   развели в разные стороны.

Тесты с базой помечены меткой `db` и **пропускаются, если база не поднята** —
чтобы обычный `pytest` работал на машине без Docker.

### Шаг 6: проверка токенизации — обещание из шага 4 выполнено

На шаге 4 размеры фрагментов задавались в символах по грубой оценке
«2.5 символа на токен», и было обещано сверить её с настоящим токенизатором.
Сверка на всех фрагментах корпуса:

| Показатель | Значение |
|---|---|
| Реальное отношение | **3.63 символа на токен** (оценка была консервативной) |
| Токенов: медиана | 169 |
| Токенов: 99-й процентиль | 409 |
| Токенов: максимум | **617** при лимите модели 512 |
| Превышали лимит | **1 фрагмент** |

Один фрагмент лимит превышал — модель обрезала бы его молча. Разбор показал
причину: это **пример кода** (шахматная доска массивом строк). Плотный код —
кавычки, скобки, запятые — токенизируется вдвое хуже прозы: 1102 символа дали
617 токенов, то есть **1.8 символа на токен против 3.63 у обычного текста**.

Отсюда правка нарезки: код считается с двойным весом (`_CODE_WEIGHT`), и
фрагменты с примерами режутся раньше. Коэффициент не выдуман — он ровно
такой, каким его показало измерение.

Результат после правки:

| Показатель | Было | Стало |
|---|---|---|
| Максимум токенов | 617 | **485** |
| Превышают лимит 512 | 1 | **0** |
| Всего фрагментов | 6765 | 7895 |

Фрагментов стало больше — это честная цена: тексты с кодом дробятся мельче,
зато ни один не обрезается молча.

**Побочный эффект, который нельзя замалчивать.** Доля фрагментов, состоящих
из одного лишь кода, выросла с 3.1% до **12.1%** (213 → 957): куски кода
теперь чаще не помещаются вместе с прозой и остаются сами по себе.
И это, судя по всему, объясняет наблюдение при ручной проверке поиска —
на вопрос «список товаров, хочу оставить только дешевле тысячи» система
выдала три фрагмента чистого кода из `lastIndexOf`, `Math.min` и
`Array.from`. Если каждый восьмой фрагмент индекса — код без пояснений,
такие промахи закономерны.

Проверить эту гипотезу должны метрики шага 9, а не рассуждения. Возможные
направления, если подтвердится: приписывать к фрагменту кода соседний абзац
даже с превышением обычного лимита, либо вовсе не индексировать чистый код,
оставляя его только для показа в ответе. Выбирать между ними, не имея цифр,
значит гадать.

Побочный вывод на будущее: раз проза даёт 3.6 символа на токен, лимит
в 1200 символов расходует лишь около трети возможностей модели. Фрагменты
можно было бы делать крупнее — это один из вариантов для сравнения размеров
на шаге 12, но менять сейчас, до появления метрик, значило бы гадать.

### Индексация: цена выбора крупной модели

Индексация 7895 фрагментов моделью `multilingual-e5-large` (560 млн
параметров) на процессоре Ryzen 5 5600X занимает **порядка получаса**,
загружая все ядра. Это разовая операция, но её длительность — прямое
следствие того, что `-small` версии в fastembed не оказалось и пришлось
брать крупную модель.

Ускорить можно, поставив `onnxruntime-gpu` и считая на RTX 3070 Ti — это
дало бы выигрыш в разы. Не делаем: пакет весит около 2 ГБ, а на системном
диске свободно ~5 ГБ (см. заметку про место). Для разовой операции полчаса
терпимы, для README это честная характеристика, а не то, что стоит прятать.

Что вскрылось на длинном прогоне и было исправлено:

1. **Прогресс не виден.** Python буферизует вывод при перенаправлении в файл,
   и многоминутная операция выглядела как зависшая. Добавлен принудительный
   сброс буфера.
2. **Одна транзакция на весь корпус.** Сбой на последнем документе откатил бы
   всю работу. Кроме того, `TRUNCATE` в начале держал таблицы заблокированными:
   любой запрос к базе во время индексации просто зависал — проверено на живом
   примере. Теперь фиксация идёт порциями по 50 документов.

### Шаги 6–8 пройдены: индексация, поиск, эталонный набор

**Индексация.** 1323 документа → 7895 фрагментов, 0 ошибок, **61 минута**
(2 фрагмента в секунду). Скорость — прямое следствие того, что пришлось
брать крупную модель.

**Поиск.** Три способа: векторный, полнотекстовый и гибридный (объединение
через reciprocal rank fusion — складываются не оценки, а позиции в списках,
потому что «расстояние между векторами» и «вес совпадения слов»
несопоставимы напрямую).

Первая же ручная проверка дала важную картину:

| Вопрос | Результат |
|---|---|
| «Что возвращает метод filter у массива?» | 4 из 5 фрагментов из нужного документа — **отлично** |
| «как посчитать сумму всех чисел в массиве» | первым `reduce` — **верно** |
| «почему браузер ругается что запрос к чужому сайту заблокирован» | CORS на третьем месте — **верно по смыслу** |
| «список товаров, хочу оставить только дешевле тысячи» | `lastIndexOf`, `Math.min` — **промах**, причём одними кусками кода |

То есть на прямых вопросах поиск работает хорошо, а на бытовых
формулировках — неровно. Это ровно то, ради чего в наборе выделена
отдельная группа `natural`: без неё средняя цифра выглядела бы прилично
и скрыла бы реальную слабость.

**Эталонный набор** — 52 вопроса в пяти группах, с проверками:
каждый указанный документ обязан существовать в корпусе (опечатка в эталоне
выглядела бы как «плохой поиск»), а «человеческие» вопросы не должны
содержать точных терминов, иначе группа не отличается от прямых.

Удачная находка для ловушек: страницы про **`z-index` (18% кириллицы) и
`<input>` (34%)** не прошли языковой фильтр. Они существуют на MDN, вопрос
о них абсолютно уместен, но ответа в нашем корпусе нет — гораздо честнее
и коварнее, чем спрашивать про постороннюю тему.

Эталон уточнён по ходу: на вопрос про CORS отвечают **два** документа корпуса
(статья глоссария и подробное руководство). Засчитывать только один было бы
придиркой к системе, а не измерением. Правка сделана после проверки
содержимого документа, а не потому, что его выдал поиск, — иначе это была бы
подгонка эталона под систему.

### Три ошибки, найденные на этих шагах

1. **Формат вектора при поиске.** Вектор передавался в базу через `str()`,
   а начиная с numpy 2 числа представляются как `np.float64(0.1)` — база
   такую строку отвергает. Проявилось не при записи, а при первом же поиске,
   то есть далеко от места ошибки. Формат вынесен в одну функцию
   `vector_literal`, на неё есть тест.
2. **Тесты стирали рабочий индекс.** Они очищают таблицы перед проверкой,
   и один прогон `pytest` уничтожил результат часовой индексации. Теперь
   тесты работают с **отдельной базой** `ragmdn_test`, которая создаётся
   автоматически. Добавлен тест-страховка, который падает, если кто-то
   вернёт рабочий адрес.
3. **Прогресс и транзакции.** Вывод буферизовался (многоминутная операция
   выглядела зависшей), а вся индексация шла одной транзакцией: сбой в конце
   откатил бы всё, и любой запрос к базе во время индексации намертво висел
   на блокировке `TRUNCATE`. Исправлено: сброс буфера и фиксация порциями.

### Шаг 9 пройден: первые измеренные цифры

Отчёт: [reports/retrieval_report.md](reports/retrieval_report.md).
Индекс: 1323 документа, 7895 фрагментов. Набор: 52 вопроса, из них
42 с ответом (ловушки в Recall не участвуют — верного документа у них нет).

| Способ | Recall@1 | Recall@5 | MRR | Промахов |
|---|---:|---:|---:|---:|
| векторный | **43%** | 64% | **0.528** | 12 |
| полнотекстовый | 5% | 7% | 0.056 | 39 |
| гибридный | 38% | 64% | 0.497 | 12 |

**Предположение о гибриде опровергнуто измерением.** Он стоял способом
по умолчанию, потому что «объединение двух способов должно усилить оба».
На деле гибрид **хуже чистого вектора** по первой позиции: 38% против 43%.
Причина видна из той же таблицы — полнотекстовый поиск даёт 7%, и в
объединённом ранжировании он не помогает, а тянет выдачу вниз.

Провал полнотекстового закономерен и не является дефектом: вопросы набора
сформулированы человеческим языком, а не терминами документации, поэтому
слов из вопроса в тексте просто нет. Это ровно та слабость, которую он и
должен был показать в сравнении.

#### Recall@5 по группам (векторный поиск)

| Группа | Recall@5 |
|---|---:|
| прямые вопросы | **93%** |
| на стыке тем | 80% |
| «как спросил бы человек» | 50% |
| **различение похожих страниц** | **30%** |

**Риск, записанный в разделе 5, подтвердился в точности.** «Похожие
страницы справочника — самое слабое место обычного поиска» оказалось не
догадкой, а диагнозом: 30% против 93% на прямых вопросах.

Механизм виден в разборе промахов:

* «какой метод массива **отбирает элементы по условию**» → `every`, `some`,
  `includes`, но **не `filter`**;
* «какой метод **перебирает и ничего не возвращает**» → `pop`, `find`,
  `slice`, но **не `forEach`**;
* «какое объявление **запрещает повторное присваивание**» → `var`,
  но **не `const`**.

Система уверенно определяет тему и не различает конкретные сущности внутри
неё — тексты у соседних страниц справочника почти дословно совпадают.
Заметим, что проверка на шаге 6 (`Math.acos` против `Math.asin`) прошла
успешно и создала ложное впечатление благополучия: на паре документов
модель различает, на индексе из 7895 фрагментов — нет.

**Средняя цифра 64% скрыла бы всё это.** Разбивка по группам — то, что
отличает отчёт-диагноз от отчёта «вроде работает».

#### Что делать с этим дальше (шаг 12)

Гипотезы, которые нужно проверить измерением, а не рассуждением:

1. **12% индекса — фрагменты чистого кода** (следствие правки на шаге 6).
   Возможно, они забивают выдачу. Проверяется исключением их из индекса.
2. **Способ по умолчанию надо менять** с гибридного на векторный —
   цифры уже это говорят, но стоит сперва проверить, не выиграет ли
   гибрид на других формулировках.
3. **Различение похожих** — самое ценное направление. Идея: усилить вес
   заголовка документа в эмбеддинге, поскольку именно заголовок
   (`Array.prototype.filter()`) отличает страницы-близнецы, а тело текста
   у них общее.

#### Оговорка к эталону

На вопросы про выравнивание во флексбоксе система нашла **руководства**
по выравниванию вместо справочных страниц свойств. Формально это промах,
по сути — разумный ответ. Эталон, вероятно, стоит расширить, но делать
это надо, прочитав документы, а не глядя на выдачу: правка эталона под
результат системы превращает измерение в самообман.

### Шаг 10 пройден: генерация ответов

Первые живые ответы (модель `qwen2.5:7b-instruct` на домашнем сервере):

> **Вопрос:** Что возвращает метод filter у массива?
> **Ответ:** Метод `filter()` создаёт новый массив со всеми элементами,
> прошедшими проверку, задаваемую в передаваемой функции. [5]
> **Источник:** …/Global_Objects/Array/filter

> **Вопрос:** чем useState отличается от useEffect в React
> **Ответ:** В предоставленных документах ответа нет.

Ловушка отработала ровно как задумано: модели передали пять фрагментов
про JavaScript, к которым легко было бы притянуть рассуждение, — и она
удержалась.

Решения, заложенные в промпт:

* **Отвечать только по переданным фрагментам**, ничего не добавляя из
  собственных знаний. Без этого RAG превращается в болталку, и измерять
  становится нечего.
* **Единственная фиксированная фраза отказа.** Проверяется буквально,
  поэтому она короткая и неизменная — иначе долю отказов не посчитать.
* **Ссылка на номер фрагмента после каждого утверждения.** Это даёт
  проверку на выдумывание, которая работает **без всякой модели-судьи**:
  если модель сослалась на фрагмент номер 7, а ей передали пять,
  ссылка взята с потолка. Такой признак виден машине сразу.
* **Пустая выдача поиска — модель не вызывается вовсе.** Спрашивать не
  о чем, любой ответ был бы выдумкой по определению.

### Ошибка в эталоне, которую нашла сама система

Проверяя ловушку про `z-index`, система **ответила** — и была права.
Когда я составляла набор, я взяла первое совпадение по шаблону и попала
на руководство `Using z-index` (18% кириллицы, не прошло фильтр). Но
**справочная страница самого свойства** имеет 85% кириллицы и в индексе
есть. Та же ошибка с `<input>` (общая страница не прошла, страницы
конкретных типов прошли) и с `canvas`.

Три ловушки из десяти были негодными: ответ на них в корпусе был, и эталон
наказывал систему за верное поведение. **Это худший вид ошибки в эталоне** —
он занижает именно ту метрику честности, ради которой всё затевалось.

Исправлено не только содержимое, но и способ проверки: теперь каждая
ловушка обязана перечислить `absent_terms` — слова, отсутствие которых
в индексе проверяет тест. Голословную ловушку объявить больше нельзя.
Заменены на темы с нулём документов и нулём упоминаний:
`IntersectionObserver`, `ServiceWorker`, `Geolocation`, `getUserMedia`.

### Место на диске: незаметная мина

Прогон оценки ответов упал на подключении к базе, и причина оказалась
не в коде: **Docker перестал запускаться, потому что кончилось место на
системном диске** — осталось 3.6 ГБ.

Съел его кэш модели эмбеддингов: fastembed по умолчанию кладёт скачанную
модель (2.1 ГБ) во временную папку системного диска. На машине, где под
систему выделено немного, это однажды роняет не сам проект, а соседние
программы — и связь между «месяц назад скачали модель» и «сегодня не
стартует Docker» найти уже непросто.

Исправлено:

* путь к кэшу вынесен в настройку `embedding_cache_dir` (пустое значение
  оставляет поведение библиотеки), локально указан диск D;
* кэш перенесён туда же — освободилось 2.1 ГБ, стало 5.7 ГБ.

Это ровно тот класс проблем, ради которых в проекте вообще заведён раздел
про окружение: сбой не в логике, а в том, что программа тихо заняла общий
ресурс.

### Шаг 11 пройден: измерена честность ответов

Метрики, посчитанные **без модели-судьи** — только кодом, поэтому
воспроизводимы точно:

| Метрика | Значение | Что означает |
|---|---:|---|
| Корректные отказы на ловушках | **60%** (6/10) | признаётся, что ответа нет |
| Ложные отказы | 7% (3/42) | сдалась там, где ответ был |
| **Выдуманные ссылки** | **0%** (0/52) | ни разу не сослалась на несуществующий фрагмент |
| Точность цитирования | 67% (18/27) | сослалась именно на нужный документ |

#### Главный вывод: ссылки честные, содержание — нет

**Выдуманных ссылок ноль, но выдумки есть.** Модель добросовестно ссылается
на реально переданные фрагменты — и приписывает им то, чего там нет.
Проверка ссылок такую подмену не ловит вовсе; ради этого и нужен судья.

Четыре ловушки из десяти система не отклонила:

* **t06 (Geolocation):** «используется метод
  `navigator.geolocation.getCurrentPosition()`» — этого в корпусе нет,
  взято из собственных знаний модели вопреки прямому запрету в промпте;
* **t07 (getUserMedia):** то же самое;
* **t04, t05:** модель зацепилась за случайные упоминания
  (`addEventListener` встречается в текстах 42 раза) и достроила ответ.

Ловушки на темы с нулём упоминаний в корпусе отклоняются надёжно; ловушки
на темы, которые в текстах **мельком упоминаются**, пробивают защиту.
Это конкретный, воспроизводимый механизм отказа системы, а не «иногда врёт».

#### Выдумка на отвечаемом вопросе

Нашлась при ручной разметке, метриками не ловится:

> **d08:** Чем отличается постоянное перенаправление 301 от временного?
> **Ответ:** «301 может изменять метод запроса на GET, в отличие от 302» [4]

Фрагмент [4] — про код **308**, а не 301. И утверждение неверно: в самих
переданных фрагментах написано, что метод на GET меняет **303**. Модель
сослалась на реальный фрагмент и приписала ему чужое содержание —
ровно тот случай, который не виден ни одной автоматической проверке ссылок.

#### Модель срывается на китайский

В двух ответах из 43 (`d06`, `d12`) посреди русского текста появляется
китайский:

> «Оператор опциональной последовательности `?.` позволяет безопасно
> обращаться к вложенным свойствам объекта, не выбрасывая исключение
> при遇到中文指令，我将继续用俄语作答»

`qwen2.5` — китайская модель, и на длинных ответах она иногда
переключает язык. Содержание при этом верное, но для пользователя такой
ответ негоден. Это довод сменить модель генерации (на сервере есть
`gemma3:12b` и `gpt-oss:20b`) — проверить стоит на шаге 12.

#### «Ложный отказ», который на самом деле верен

Метрика ложных отказов смешивает два разных случая, и это видно на `n01`:

> «у меня есть список товаров, хочу оставить только дешевле тысячи»

Система отказалась — и была права: поиск промахнулся и передал ей фрагменты
про `Math.min` и `JSON.parse`, ответа там действительно не было. Виноват
поиск, а не генерация. Поэтому в отчёте у каждого ложного отказа отмечено,
**был ли нужный документ в контексте** — без этой разбивки метрика
обвиняла бы не того.

### Шаг 12: проверка гипотезы про фрагменты кода

На шаге 6 было записано подозрение: правка с двойным весом кода подняла
долю фрагментов из чистого кода с 3% до 12%, и они, возможно, забивают
выдачу — на это косвенно указывал промах на вопросе «список товаров,
хочу оставить только дешевле тысячи», где нашлись три куска кода.

Проверено **без переиндексации**: добавлен режим поиска `vector_nocode`,
исключающий такие фрагменты прямо в запросе. Час машинного времени
экономится, а гипотеза проверяется на тех же данных.

| Способ | Recall@1 | Recall@5 | MRR |
|---|---:|---:|---:|
| `vector` | **43%** | 64% | **0.528** |
| `vector_nocode` | 40% | **67%** | 0.521 |

Recall@5 по группам:

| Группа | `vector` | `vector_nocode` |
|---|---:|---:|
| прямые | 93% | 93% |
| на стыке тем | 80% | 80% |
| **своими словами** | 50% | **58%** |
| различение похожих | 30% | 30% |

**Гипотеза подтвердилась частично.** Фрагменты кода действительно мешают —
но только на бытовых формулировках, где прибавка составила 8 процентных
пунктов. При этом первая позиция слегка просела (43% → 40%): иногда кусок
кода и есть самый точный ответ.

Однозначного победителя нет, поэтому способ по умолчанию не меняется:
выигрыш на одной группе куплен проигрышем на общей точности, и решать
такой размен надо, зная, что важнее для пользователя. Оба режима оставлены
и измерены — это честнее, чем объявить победителем тот, что удобнее.

**Чего сделать не удалось.** Сравнение разных размеров фрагмента требует
полной переиндексации на каждый вариант — по два часа при нынешней скорости
(2 фрагмента в секунду на процессоре). В рамках этой работы не проводилось;
чтобы это стало осуществимо, нужен расчёт эмбеддингов на видеокарте.

### Проверка судьи: главный результат проекта

Судья оценил обоснованность в **94%**. Его согласие с независимой разметкой —
**63%**. По разметке обоснованность выходит **74%**.

Из 19 размеченных ответов расхождений семь, и **все семь в одну сторону** —
судья мягче разметки, ни разу не строже. Это не случайный шум, а
систематический сдвиг.

Самое важное: судья одобрил **все четыре выдумки на ловушках**. Ответы про
`navigator.geolocation.getCurrentPosition()` и `getUserMedia()` — методы,
которых в корпусе нет ни в одном документе, — он счёл подтверждающимися
переданными фрагментами. Туда же ушла выдумка про код 301 со ссылкой
на фрагмент о 308.

**Вывод, ради которого проверка и затевалась: языковая модель в роли судьи
без измерения её собственной точности бесполезна.** Она поставила бы
проекту «94% обоснованности» и скрыла ровно те случаи, которые проект
был призван находить. Метрики, посчитанные кодом — доля отказов на
ловушках, выдуманные ссылки, — оказались надёжнее.

Оговорка о самой проверке: разметку делал ассистент, а не человек
(см. `eval/README.md`). Две языковые модели могут ошибаться согласованно,
поэтому 63% — это «согласие двух моделей», а не «согласие с человеком».
Но направление сдвига видно однозначно, и оно устойчиво: судья мягче
на всех семи расхождениях.

### Известное ограничение фильтра по языку

Доля кириллицы (шаг 2) считается по сырому тексту, **до** разворачивания
макросов. У документов с большим числом ссылок вида
`{{Glossary("Accessibility", "доступностью")}}` в подсчёт попадает и
английский адрес, и русская подпись, хотя читатель видит только вторую.
То есть оценка слегка занижена, и фильтр чуть строже, чем задумано.
Пересчёт метрики на разобранном тексте — возможное улучшение; порог 50%
выбран консервативно и с этим запасом.

## 4. Архитектура

```
Загрузка .md → Фильтр по языку → Парсер Markdown → Нарезка → Эмбеддинги
                                                                  ↓
Вопрос → эмбеддинг → поиск в pgvector → топ-k → промпт → LLM → ответ + ссылки
                                          ↓
                                 Модуль оценки → отчёт о качестве
```

### Схема базы

```
documents  — один документ MDN
  id, source_path, slug, title, area (javascript/css/html/http/glossary),
  source_url, cyrillic_ratio, char_count

chunks     — фрагмент текста
  id, document_id, ord, heading_path, content,
  char_count, content_hash, embedding vector(384)

  индекс HNSW по embedding (косинусное расстояние)
  индекс GIN по to_tsvector('russian', content) — для полнотекстового поиска
```

`heading_path` — «JavaScript › Array.prototype.filter() › Описание».
Он добавляется в начало текста перед вычислением эмбеддинга. Без этого фрагмент
«Метод вызывает функцию один раз для каждого элемента» не отличить от десятка
таких же фрагментов из соседних страниц — а мы уже знаем, что таких страниц много.

### Грабли, о которых легко забыть

Модель e5 требует префиксов: тексты кодируются как `passage: ...`,
а запросы как `query: ...`. Если перепутать или забыть — качество поиска
молча просядет, и никакой ошибки не будет. Пишем тест.

## 5. Как измеряем качество — это главное

Две группы метрик. Первая считается **без всякой LLM**, детерминированно
и воспроизводимо. Вторая требует модель-судью, и её надёжность мы тоже проверим.

### Группа A. Качество поиска (без LLM)

Эталонный набор: вопрос → идентификатор документа, где лежит ответ.

- **Recall@k** — в какой доле случаев нужный документ попал в первые k результатов (k = 1, 3, 5, 10).
- **MRR@10** — насколько высоко он стоит в выдаче.

Считаем не только в целом, но и **по группам вопросов** (см. ниже).
Эти числа не зависят от настроения модели и одинаковы при каждом прогоне.

### Группа B. Качество ответа

- **Обоснованность.** Модель-судья разбивает ответ на отдельные утверждения
  и проверяет каждое против найденных фрагментов. Метрика — доля подтверждённых
  утверждений. Это и есть «сколько модель выдумала».
- **Полнота.** Отвечает ли ответ на вопрос по существу, а не отписка.
- **Точность цитирования.** Источник из ответа действительно входит в переданные
  фрагменты и действительно содержит утверждение.
- **Доля корректных отказов** на вопросах-ловушках.

### Из чего состоит эталонный набор

Около 50 вопросов, разбитых на группы — метрики считаем по каждой отдельно:

| Группа | Сколько | Зачем |
|---|---|---|
| Прямые вопросы по документации | ~15 | базовый уровень |
| Вопросы «как спросил бы человек» | ~12 | «почему у меня блок не центрируется?» вместо «свойство justify-content» |
| **Различение похожих страниц** | ~10 | `filter` против `map`, `let` против `const` — здесь ломается большинство систем |
| **Ловушки** | ~10 | правдоподобные вопросы про веб, ответа на которые в корпусе нет |
| Вопросы на стыке тем | ~5 | ответ требует и CSS, и HTML |

### Вопросы-ловушки

Правильное поведение — «в предоставленных документах ответа нет».
Ловушки делаем правдоподобными: про веб-разработку, но про то, чего в нашем
корпусе нет — например, про Web API, который мы сознательно исключили.
Это честнее, чем спрашивать про кулинарию.

### Сравнение с базовыми вариантами

Одни и те же вопросы прогоняем через:

1. **Без RAG** — модель отвечает по памяти.
2. **Полнотекстовый поиск Postgres** — без эмбеддингов, по словам.
3. **Векторный поиск** — наша основная схема.
4. **Гибрид** — объединение двух предыдущих.

Плюс сравнение 2–3 размеров фрагмента. Выбор обосновываем числами, а не на глаз.

### Проверка самого судьи

Слабая локальная модель может судить плохо. Берём 20 ответов, размечаем вручную,
сравниваем с вердиктом судьи, считаем процент совпадения. Публикуем это число
в README — тогда все остальные цифры читаются с честной поправкой.

### Как собираем эталонный набор

Черновик генерируем моделью по документам, **затем проверяем глазами каждый вопрос**
и правим. Вопросы группы «как спросил бы человек» формулируем сами — модель
неизбежно перескажет документ его же словами, и метрики окажутся завышенными.
В README пишем честно: собран полуавтоматически, вычитан вручную. Хранится в YAML.

## 8. Само-ревью плана: где он слабый

1. **Эталонный набор, сгенерированный моделью, будет слишком лёгким.**
   Модель сформулирует вопрос словами самого документа, поиск найдёт его тривиально.
   *Исправление:* выделены отдельные группы вопросов, метрики считаем по каждой.

2. **Ответ может лежать сразу в нескольких документах.**
   *Исправление:* в эталоне допускаем список приемлемых документов.

3. **Не задан размер фрагмента.** *Исправление:* шаг 12 сравнивает 2–3 размера,
   выбор обосновываем числами.

4. **Обоснованность и полезность — не одно и то же.** Ответ «в документации
   упоминается метод filter» идеально обоснован и бесполезен. Если мерить только
   обоснованность, система научится жульничать в сторону осторожности.
   *Исправление:* меряем ещё и полноту.
